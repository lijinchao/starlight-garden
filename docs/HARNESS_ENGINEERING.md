# 星光花园 - Harness 工程

## 1. 目的

Harness 工程的目标是把“产品方向正确、功能可验证、文档代码一致”变成仓库内可执行的反馈回路，而不是依赖临时口头判断。

本仓库采用的原则参考 OpenAI《工程技术：在智能体优先的世界中利用 Codex》一文：仓库应成为记录系统，`AGENTS.md` 作为地图，深层产品、架构、验证信息放入结构化文档；同时用测试、结构检查和可观测入口让 Agent 能直接验证自己的改动。

参考链接：https://openai.com/zh-Hans-CN/index/harness-engineering/

## 2. 本项目的 Harness 边界

当前项目定位仍是：

> 治愈题材三消原型 + 基础花园循环雏形

因此 Harness 不追求覆盖所有未来系统，而只保护当前最重要的产品不变量：

- 玩家每打一局都能明确获得或保留某种成长。
- 局内奖励能进入花园库存或星光资源。
- 花园成长能通过星光反哺局内，并让星光投入花园装饰形成可见长期目标。
- 失败后的“休息时刻”必须是规则，不只是文案。
- 每个迭代必须说明服务的产品目标、用户感知结果和验证方式。

## 3. Harness 分层

### 3.1 知识地图层

`AGENTS.md` 只做入口地图，不承载全部细节。Agent 进入仓库后必须优先阅读：

1. `README.md`
2. `docs/STATUS_AND_ITERATION_PLAN.md`
3. 当前迭代文档，默认是 `docs/ITERATION_G_TASK_BREAKDOWN.md`
4. `docs/HARNESS_ENGINEERING.md`
5. `docs/MANUAL_VERIFICATION_GUIDE.md`

### 3.2 目标对齐层

每次功能改动必须能映射到至少一个目标：

- 闭合主循环
- 强化局外成长
- 强化治愈体验
- 增强内容留存
- 优化资源反哺

如果一个改动只增加 UI、文案或数据配置，但没有形成玩家可感知的规则变化，应视为未完成。

### 3.3 机械检查层

`scripts/tools/harness_check.gd` 负责静态检查仓库是否仍满足 Harness 基线：

- 核心文档存在且可被入口文档发现。
- 当前迭代文档包含产品目标、用户感知、验证清单、完成定义。
- 手动验证文档覆盖胜利结算、花园、合成、星光祝福、失败保底、续关、花园装饰。
- 20 个关卡配置均包含目标、可用元素、奖励、首通奖励。
- 关卡奖励至少形成 3 个阶段，避免所有关卡掉落无差异。
- `project.godot` 注册核心结算、经济、存档、合成、装饰服务。

### 3.4 自动化测试层

`tests/TestRunner.gd` 负责运行玩法和资源流测试，当前重点保护：

- 统一结算
- 首通奖励唯一性
- 配置化奖励读取
- 失败保底
- 连续失败鼓励
- 星光消费和开局祝福
- 花园种植、收获、合成、装饰购买
- 存档结构迁移

### 3.5 手动验证层

`docs/MANUAL_VERIFICATION_GUIDE.md` 负责覆盖自动化测试不容易证明的用户感知：

- 玩家能否看懂结算奖励。
- 玩家能否在 3 局内理解花园成长。
- 玩家是否能感知失败后不是白玩。
- 星光的续关、开局祝福、花园装饰用途是否清晰。

## 4. 统一运行入口

完整 Harness 回归使用：

```bash
./run_harness.sh
```

该命令会先无界面导入新增图片等项目资源，再运行结构与目标检查和现有 Godot 测试。这样首次检出项目时，资源加载测试也能稳定运行。若只需要运行玩法测试，可继续使用：

```bash
./run_tests.sh
```

如果 Godot 不在 `PATH`，需要设置：

```bash
GODOT_BIN="/Users/jacklee/Downloads/Godot.app/Contents/MacOS/Godot" ./run_harness.sh
```

## 5. 交付完成定义

任何后续迭代在标记完成前，至少满足以下条件：

1. 当前迭代文档说明本轮服务的产品目标和不做范围。
2. 功能项有用户可感知结果和验证方式。
3. 涉及资源流、奖励、存档、失败/续关、配置驱动行为时，有自动化测试。
4. 难以自动化证明的体验变化，补入手动验证步骤。
5. `./run_harness.sh` 可运行并通过，或在交付说明中明确阻塞原因。

## 6. 维护规则

当发现 Agent 反复犯同类错误时，优先把判断编码到以下位置之一：

- 可机械检查的问题，加入 `scripts/tools/harness_check.gd`。
- 资源流或规则问题，加入 `tests/TestRunner.gd`。
- 用户感知问题，加入 `docs/MANUAL_VERIFICATION_GUIDE.md`。
- 产品方向问题，更新当前迭代文档或 `docs/STATUS_AND_ITERATION_PLAN.md`。

不要把所有细节继续堆进 `AGENTS.md`。`AGENTS.md` 应保持为地图，深层规则放在可维护、可验证的文档和脚本中。
