## 1. 总体结论

### 1.1 产品方向没有根本偏移

当前真正成立的体验主线是：

`轻量三消 -> 带回花种 -> 花园恢复 -> 下一局继续照料`

“前三局恢复花园”和“四连触发清风唤醒”比最初泛化的“女性向消除 + 合成 + 剧情 + 社交”更聚焦，也更适合微信或抖音小游戏的短局体验。

### 1.2 产品范围仍然偏宽

花语、每日任务、装饰、合成、祝福、续关和局内辅助都已有最小实现。前三局虽然隐藏了它们，但多数能力在 `total_runs >= 3` 时集中开放，复杂度只是被延后，没有真正分层。

当前最需要验证的不是“还能增加什么”，而是：

- 玩家是否理解自己在修复花园。
- 清风唤醒是否真的让局内更有趣。
- 第 4 局的入口集中开放是否造成新的流失点。
- 失败也推进恢复是否保留了足够的成功价值。

### 1.3 工程仍可驾驭，但已接近原型架构上限

核心规则、关卡状态和结算已具备自动化保护，`Board` 也已经是实际规则真源。但仓库仍有重复控制器、旧场景、超大 UI 脚本、12 个 Autoload、直接字典存档和单文件测试集等债务。

结论不是立即重写，而是停止扩系统，先收口唯一入口、状态边界、平台预算和验证方式。

## 2. 当前产品基线

### 2.1 一句话定位

> 一款通过短局花朵三消，逐步唤醒花园角落的治愈系小游戏原型。

“合成、花语、每日、装饰”是延后开放的辅助层，不是首屏卖点，也不是当前差异化核心。

### 2.2 当前核心体验优先级

1. 单局交换、消除、连锁是否轻松顺畅。
2. 当前关卡是否明确说明正在唤醒哪个角落。
3. 四连的清风唤醒是否可见、可理解且真实推进目标。
4. 结算奖励是否自然进入花园恢复。
5. 花园变化是否构成再打一局的理由。

### 2.3 当前不应继续扩展

- 第二套或第三套货币。
- 更多每日/活动入口。
- 重剧情章节。
- 排行榜、好友、赛季和公会。
- 大型自由装扮系统。
- 未经过局内验证就增加传统炸弹和彩球体系。

## 3. 产品偏移与冲突裁决

| 冲突 | 当前事实 | 裁决 |
|------|----------|------|
| “消除 + 合成”还是“修复花园” | 合成存在但前三局隐藏，恢复反馈是当前差异化 | 对外定位以“花园修复三消”为主，合成降为 Meta 能力 |
| MVP 还是 Pre-MVP | 主场景旧文案写 `1.0.0 MVP`，状态与迭代文档写 Pre-MVP | 统一按 Pre-MVP；未完成真实平台接入、性能和用户验证前不称 MVP |
| 微信还是微信/抖音 | 旧 GDD、导出与运行文档只写微信；产品讨论包含抖音 | 当前是 Godot Web 原型，平台未接入；平台选择保持开放，但不宣称已支持 |
| 迭代 G 是否完成 | 规则、素材和自动化已完成，尚无用户验证数据 | 工程实现完成，产品验证未完成，不进入新玩法扩张 |
| 失败是否应推进恢复 | 当前胜利和失败都会累计总局数并推进前三局恢复 | 保留低压设计，但必须观察是否削弱通关成就感 |
| 第 4 局是否完成渐进解锁 | 多数入口使用同一个 `total_runs >= 3` 阈值 | 判定为“延后开放”，不是完整渐进解锁；后续应拆成事件驱动解锁 |

## 4. 当前运行架构

```text
scenes/main.tscn
  -> SceneManager
      -> MainMenu
      -> SimpleGameController
          -> LevelSystem         关卡配置、步数、目标、胜负
          -> Board               棋盘、交换、匹配、掉落、连锁
          -> BoardVisual         棋子表现、输入、动画、清风特效
          -> SettlementService   结算构建与奖励发放
      -> GardenUI
      -> FlowerLanguageUI / DailyGiftUI / SettingsUI

全局状态与服务
  SaveManager -> Economy / Garden / FlowerLanguage / Daily / Decoration
  GameManager -> 场景状态与关卡完成通知
  PopupManager / TutorialManager / AudioManager -> 横切体验能力
```

### 4.1 当前唯一有效入口

- 主场景：`scenes/main.tscn`
- 场景编排：`scripts/systems/SceneManager.gd`
- 局内控制器：`scripts/ui/SimpleGameController.gd`
- 局内规则真源：`scripts/core/Board.gd`
- 关卡状态真源：`scripts/systems/LevelSystem.gd`
- 统一结算：`scripts/autoload/SettlementService.gd`

`GameController.gd`、`GameHUD.gd`、`TileVisual.gd`、`scenes/game/game.tscn` 和 `game_complete.tscn` 当前不在正式运行链路中，应视为待隔离的旧实现，而不是并行架构。

## 5. 技术风险清单

### P0：下一轮应优先处理

1. **重复运行路径**

   旧控制器和旧 game 场景仍可被误读、误改，已经与当前 API 不一致。应先建立弃用清单，再删除或移入明确的历史目录。

2. **平台和包体没有工程预算**

   当前原始图片约 18MB，Web 导出使用 `all_resources`，会把未使用旧场景和资源一起打包。尚无首包、分包、纹理尺寸、内存峰值、加载时间和低端机帧率门槛。

3. **迭代 G 缺少产品证据**

   `261/261` 自动化测试证明规则正确，不能证明“休闲有趣”或“愿意再打一局”。必须补短流程试玩记录或埋点口径。

4. **第 4 局解锁断层**

   花语、每日、合成、装饰、祝福、续关和局内辅助大多共享同一阈值。应按玩家行为拆分，而不是继续增加入口。

### P1：进入 MVP 前处理

1. **全局服务过多**：12 个 Autoload 让任意 UI 都能直接读写状态，依赖方向难以约束。
2. **存档边界过松**：`SaveManager` 返回可变 `Dictionary`，调用方取出、修改、再整体写回，缺少事务和类型契约。
3. **UI 脚本过大**：`GardenUI.gd`、`MainMenu.gd`、`PopupManager.gd` 同时承担建树、样式、状态映射和业务操作。
4. **测试单体化**：`TestRunner.gd` 接近千行，依赖全局单例重置，新增并行测试或失败定位会越来越困难。
5. **死配置存在**：关卡配置包含 `special_elements`，常量也定义炸弹和彩虹花，但当前 `Board` 不消费该配置。
6. **场景内嵌脚本**：`main.tscn` 和旧 game 场景包含较长内嵌脚本，不利于复用、审查和测试。

### P2：规模扩大后再处理

- 将所有 Autoload 改成依赖注入。
- 全面改用 Resource 或强类型数据模型。
- 重写为完整 ECS、事件总线或插件化架构。

这些方案当前成本高于收益，不应作为下一轮目标。

## 6. 文档权威顺序

发生冲突时按以下顺序判断：

1. 当前可运行代码、关卡配置和自动化测试。
2. 本文档与 `STATUS_AND_ITERATION_PLAN.md`。
3. 当前迭代文档 `ITERATION_H_TASK_BREAKDOWN.md`；迭代 G 保留为玩法实现依据。
4. `GAME_DESIGN.md`，仅代表长期产品愿景。
5. `DEVELOPMENT_PLAN.md`、`AI_DEVELOPMENT_PLAN.md`，仅作历史规划参考。
6. `PROJECT_STATUS_REVIEW.md`、`TECH_REMEDIATION_PLAN.md`，仅作历史问题来源，问题是否仍存在必须重新核对代码。

## 7. 下一阶段建议：先设验证闸门

在新建迭代 H 前，先完成以下闸门：

### 产品验证

- 至少 5 名目标用户完成前 5 关。
- 记录第 1 局完成率、第 3 局到达率、第 4 局继续率。
- 询问玩家能否复述“这一局在修复哪里”。
- 记录清风唤醒首次触发关卡、触发次数和是否被注意到。
- 观察第 4 局入口开放后的停顿、误触和返回行为。

### 工程收敛

- 隔离或删除未运行的局内控制器和旧场景。
- 建立平台能力接口清单，但暂不接入真实 SDK。
- 为 Web 导出增加资源排除和包体报告。
- 将 Meta 解锁条件集中到单一策略服务。
- 把素材、平台和运行链路检查加入 Harness。

只有上述结果表明局内体验成立，才决定下一轮是继续强化清风机制、调整第 4 局解锁，还是补第二种局内主题机制。
