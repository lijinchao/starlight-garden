## 文档信息

| 项目 | 内容 |
|------|------|
| 文档性质 | 当前产品裁决 / 架构基线 / 冲突处理依据 |
| 更新时间 | 2026-08-25 |

本文用于回答三个问题：当前产品是否跑偏、工程是否仍可驾驭、发生文档冲突时以什么为准。

目标用户、使用场景、流行玩法取舍和下一轮试玩门槛以 [PRODUCT_THEME_AND_GAMEPLAY_REVIEW.md](./PRODUCT_THEME_AND_GAMEPLAY_REVIEW.md) 为准。

迭代 I、J 已闭合导航、奖励、渐进解锁和花园空间交互。迭代 K 把“清风”做成可规划的方向路径，迭代 L 收敛为“每日风庭 + 晨露连锁”。2026-08-25 项目所有者无讲解试玩后给出负反馈：核心消消乐复杂度弱、不好玩，没有“消完再部署”的落点，整体没有情感波动与情绪价值。迭代 M 因此先做减法，把普通关收敛回一条主目标，再补“消除 → 可见收获”的即时手感与情绪闭环；在核心手感成立前不再扩每日内容。

## 1. 总体结论

### 1.1 产品方向没有根本偏移

当前真正成立的体验主线是：

`轻量三消 -> 带回花种 -> 花园恢复 -> 下一局继续照料`

“前三局恢复花园”和“四连触发清风唤醒”比最初泛化的“女性向消除 + 合成 + 剧情 + 社交”更聚焦，也更适合微信或抖音小游戏的短局体验。

### 1.2 产品范围仍然偏宽

花语、每日任务、装饰、合成、祝福、续关和局内辅助都已有最小实现。I-3 已将主要 Meta 能力从 `total_runs >= 3` 集中开放改为行为触发、固定队列和单任务推进；系统数量仍偏多，但认知负担已经分层。

当前最需要验证的不是“还能增加什么”，而是：

- 玩家是否理解自己在修复花园。
- 清风唤醒是否真的让局内更有趣。
- 行为驱动的单入口解锁是否降低第 4 局后的犹豫和流失。
- 失败也推进恢复是否保留了足够的成功价值。

### 1.3 工程仍可驾驭，但已接近原型架构上限

核心规则、关卡状态和结算已具备自动化保护，`Board` 也已经是实际规则真源，棋盘随机已改为可复现的局部种子。测试已从单文件拆分为 `tests/suites/`，旧控制器与旧场景已删除；仓库仍有超大 UI 脚本、14 个 Autoload 和直接字典存档等债务。

结论不是立即重写，而是停止扩系统，先收口唯一入口、状态边界、平台预算和验证方式。

## 2. 当前产品基线

### 2.1 一句话定位

> 一款通过短局花朵三消，逐步唤醒花园角落的治愈系小游戏原型。

“合成、花语、每日、装饰”是延后开放的辅助层，不是首屏卖点，也不是当前差异化核心。

### 2.2 当前核心体验优先级

1. 单局交换、消除、连锁是否轻松顺畅。
2. 当前关卡是否明确说明正在唤醒哪个角落。
3. 四连的清风唤醒是否可见、可理解且真实推进目标。
4. 结算奖励是否自然进入花园恢复。
5. 花园变化是否构成再打一局的理由。

### 2.3 当前不应继续扩展

- 第二套或第三套货币。
- 更多每日/活动入口。
- 重剧情章节。
- 排行榜、好友、赛季和公会。
- 大型自由装扮系统。
- 未经过局内验证就增加传统炸弹和彩球体系。

## 3. 产品偏移与冲突裁决

| 冲突 | 当前事实 | 裁决 |
|------|----------|------|
| “消除 + 合成”还是“修复花园” | 合成存在但前三局隐藏，恢复反馈是当前差异化 | 对外定位以“花园修复三消”为主，合成降为 Meta 能力 |
| MVP 还是 Pre-MVP | 主场景旧文案写 `1.0.0 MVP`，状态与迭代文档写 Pre-MVP | 统一按 Pre-MVP；未完成真实平台接入、性能和用户验证前不称 MVP |
| 微信还是微信/抖音 | 旧 GDD、导出与运行文档只写微信；产品讨论包含抖音 | 当前是 Godot Web 原型，平台未接入；平台选择保持开放，但不宣称已支持 |
| 迭代 G 是否完成 | 规则、素材和自动化已完成，尚无用户验证数据 | 工程实现完成，产品验证未完成，不进入新玩法扩张 |
| 失败是否应推进恢复 | 当前胜利和失败都会累计总局数并推进前三局恢复 | 保留低压设计，但必须观察是否削弱通关成就感 |
| 第 4 局是否完成渐进解锁 | 主要 Meta 能力按行为进入固定队列，每次主页回访最多推进一个任务 | 工程实现完成；是否降低犹豫由 5 人观察式试玩裁决 |
| 每日风庭是否推进线性关卡 | 每日挑战复用局内控制器，但走独立结算，不发放普通奖励、不推进线性关卡 | 保留“每日内容 + 线性关卡”双轨；每日成绩只记本地最佳 |

## 4. 当前运行架构

```text
scenes/main.tscn
  -> SceneManager
      -> MainMenu
      -> SimpleGameController
          -> LevelSystem         关卡配置、步数、目标、胜负
          -> Board               棋盘、交换、匹配、掉落、连锁、清风路径、晨露连锁
          -> BoardVisual         棋子表现、输入、动画、清风特效
          -> SettlementService   结算构建与奖励发放
      -> GardenUI
      -> FlowerLanguageUI / DailyGiftUI（含今日风庭入口） / SettingsUI

全局状态与服务
  SaveManager -> Economy / Garden / FlowerLanguage / Daily / DailyChallenge / Decoration
  GameManager -> 场景状态与关卡完成通知
  PopupManager / TutorialManager / AudioManager -> 横切体验能力
```

### 4.1 当前唯一有效入口

- 主场景：`scenes/main.tscn`
- 场景编排：`scripts/systems/SceneManager.gd`
- 局内控制器：`scripts/ui/SimpleGameController.gd`
- 局内规则真源：`scripts/core/Board.gd`
- 关卡状态真源：`scripts/systems/LevelSystem.gd`
- 统一结算：`scripts/autoload/SettlementService.gd`

`GameController.gd`、`GameHUD.gd`、`TileVisual.gd`、`scenes/game/game.tscn` 和 `game_complete.tscn` 已确认不在任何运行链路、测试或场景引用中，本轮已删除，`scripts/` 与 `scenes/` 不再保留并行实现。

## 5. 技术风险清单

### P0：下一轮应优先处理

1. **核心玩法已被真实试玩判为不成立**

   2026-08-25 项目所有者试玩反馈：消消乐复杂度弱、不好玩，消除与花园没有连续因果，一局没有情绪波动。迭代 M 必须先做规则减法并补“消除 → 可见收获”的即时反馈，再谈任何内容扩展。

2. **每日挑战可完成性只有弱证据**

   `tests/suites/meta_suite.gd` 已验证 12 种母版变换都有有效交换且同日棋盘可复现，但没有证明 26 步内一定可通关；可完成性实际由 L-3 的 `35%-65%` 通关率区间裁决。

3. **渐进解锁仍待用户验证**

   工程侧已完成行为触发、等待队列和单任务推荐；仍需观察玩家是否理解新入口为何出现、完成后得到什么，以及是否愿意继续下一关。

4. **平台和包体没有工程预算**

   当前原始图片约 18MB，Web 导出使用 `all_resources`。旧场景已删除，但尚无首包、分包、纹理尺寸、内存峰值、加载时间和低端机帧率门槛。

### P1：进入 MVP 前处理

1. **全局服务过多**：14 个 Autoload 让任意 UI 都能直接读写状态，依赖方向难以约束。
2. **存档边界过松**：`SaveManager` 返回可变 `Dictionary`，调用方取出、修改、再整体写回，缺少事务和类型契约。
3. **UI 脚本过大**：`GardenUI.gd`、`MainMenu.gd`、`PopupManager.gd` 同时承担建树、样式、状态映射和业务操作。
4. **测试已拆分，但仍依赖全局单例**：`TestRunner.gd` 已缩到 175 行并拆成 `tests/suites/` 下的多个套件，但各套件仍依赖全局单例重置，并行执行与失败定位仍受限。
5. **死配置存在**：关卡配置包含 `special_elements`，常量也定义炸弹和彩虹花，但当前 `Board` 不消费该配置。
6. **场景内嵌脚本**：`main.tscn` 仍含较长内嵌脚本，不利于复用、审查和测试。

### P2：规模扩大后再处理

- 将所有 Autoload 改成依赖注入。
- 全面改用 Resource 或强类型数据模型。
- 重写为完整 ECS、事件总线或插件化架构。

这些方案当前成本高于收益，不应作为下一轮目标。

## 6. 文档权威顺序

发生冲突时按以下顺序判断：

1. 当前可运行代码、关卡配置和自动化测试。
2. 本文档与 `STATUS_AND_ITERATION_PLAN.md`。
3. 当前迭代文档 `ITERATION_P_SINGLE_LOOP_PUZZLE_PLAN.md`；迭代 O/N/M 保留为反馈层与对象依据，迭代 K 保留为清风路径依据。
4. `GAME_DESIGN.md`，仅代表长期产品愿景。
5. `DEVELOPMENT_PLAN.md`、`AI_DEVELOPMENT_PLAN.md`，仅作历史规划参考。
6. `PROJECT_STATUS_REVIEW.md`、`TECH_REMEDIATION_PLAN.md`，仅作历史问题来源，问题是否仍存在必须重新核对代码。

## 7. 下一阶段建议：先完成迭代 M 的核心手感闸门

### 产品验证（迭代 M）

- 至少 3 名目标用户无讲解各体验 2 局。
- 能说清普通关目标，不再被多目标争夺注意力。
- 能指出“我让花园哪里变了”。
- 能指出一局里的关键转折或最爽时刻。
- 至少 `4/5` 认为结算回应了本局发生的事，而不是只报数字。

### 工程收敛

- 旧控制器与旧场景已删除。
- 平台能力接口清单与 Web 导出包体报告仍待建立，但暂不接入真实 SDK。
- Meta 解锁条件已集中到单一策略服务；后续只补试玩反馈，不继续扩入口。

只有 L-3 通过，才决定是扩展每日布局、调整花苞反馈，还是终止每日模式扩展。
