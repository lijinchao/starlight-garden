## 一、方案目标

本方案不以“继续堆功能”为优先目标，而以“先收敛结构，再补闭环”为原则。

整改期的核心目标为：

1. 修复当前已识别的真实逻辑缺陷
2. 收敛局内三消系统的数据流与职责边界
3. 让关卡配置真正驱动棋盘行为
4. 建立最小可运行的局外成长闭环
5. 补齐关键自动化测试，降低后续迭代风险

整改完成后的目标状态应为：

```text
关卡配置 -> 棋盘规则 -> 结算奖励 -> 花园成长 -> 资源回流
```

---

## 二、整改原则

### 2.1 原则一：只保留一套局内规则真源

局内核心规则必须由一个模块统一管理，避免：
- 逻辑重复
- 表现与规则不一致
- 不同控制器间行为漂移

### 2.2 原则二：优先修复会影响进度与扩展的结构问题

优先级高于新增内容的事项包括：
- 命名不一致导致的逻辑错误
- 配置不生效
- 数据模型不统一
- 测试不可覆盖关键路径

### 2.3 原则三：MVP 闭环优先于内容扩展

在主循环未闭合前，不建议继续扩展：
- 花语
- 剧情
- 社交
- 大量新关卡
- 大量特殊玩法变体

### 2.4 原则四：每阶段必须有可验证验收标准

每一阶段必须至少满足：
- 有明确代码产出
- 有明确测试或验证方式
- 有明确完成判定

## 四、阶段划分

本轮整改建议拆为 4 个阶段，预计总周期为 **2.5 到 4 周**。

### 阶段总览

| 阶段 | 名称 | 目标 | 预计周期 |
|------|------|------|----------|
| Phase 1 | 结构止血期 | 修复真实 bug，统一规则入口 | 3-5天 |
| Phase 2 | 局内收敛期 | 让关卡配置驱动棋盘，完成局内数据流收敛 | 5-7天 |
| Phase 3 | MVP 闭环期 | 打通“过关奖励 -> 花园成长 -> 资源回流” | 5-8天 |
| Phase 4 | 稳定性补强期 | 补测试、补验证、补基础可维护性 | 3-5天 |

## 五、Phase 1：结构止血期

### 5.1 阶段目标

快速修复当前最容易影响功能正确性和开发效率的问题，避免错误继续扩散。

### 5.2 主要任务

#### T1. 修复关卡字段命名不一致

问题：
- `LevelSystem` 使用 `current_level_id`
- `GameController` 使用 `current_level`

整改动作：
- 统一关卡字段命名
- 修复重开关卡、通关解锁、存档推进相关逻辑

建议方案：
- 保留 `current_level_id`
- 所有调用方统一改为该字段

#### T2. 统一测试启动方式

问题：
- 旧测试命令使用方式错误
- 测试可运行性依赖人工记忆正确命令

整改动作：
- 修正 `run_tests.sh`
- 使用 Godot 4 可运行的场景启动命令
- 写清楚本地 Godot 可执行路径配置方式

#### T3. 标记并隔离重复逻辑入口

问题：
- `Board.gd`
- `GameController.gd`
- `SimpleGameController.gd`

三处都在处理交换、匹配、下落流程。

整改动作：
- 明确当前“临时唯一有效流程”由哪个模块承担
- 先禁用或标记冗余路径，避免后续继续在错误入口上加功能

建议方案：
- 以 `Board.gd` 作为规则层
- `GameController` / `SimpleGameController` 仅保留表现和流程编排

### 5.3 交付物

- 统一后的关卡字段命名
- 修正后的测试脚本
- 一版职责说明注释或内部约定文档

### 5.4 验收标准

- 通关后可正确推进到下一关
- 重开当前关卡行为正确
- 测试可通过单条命令运行
- 新增功能时不会再出现“改 A 忘 B”的重复入口问题

### 5.5 风险

- 若 Phase 1 只修 bug 不收口职责，后续 Phase 2 会返工

## 六、Phase 2：局内收敛期

### 6.1 阶段目标

让局内系统形成清晰的数据流：

```text
LevelSystem -> Board -> BoardVisual -> Controller/HUD
```

### 6.2 主要任务

#### T4. 让 `Board` 接受关卡配置初始化

问题：
- 当前棋盘元素池写死为 6 种
- 不读取 `LevelSystem` 提供的 `available_types`

整改动作：
- 为 `Board` 增加初始化参数
- 支持从关卡配置读取元素池
- 支持关卡限定元素数量

建议接口：

```text
board.initialize_from_level(level_config)
```

#### T5. 收敛匹配、下落、补牌逻辑到 `Board`

问题：
- 规则实现散落在控制器和核心层

整改动作：
- `Board` 负责：
  - 交换是否合法
  - 匹配检测
  - 消除
  - 掉落
  - 补牌
  - 连锁
- `GameController` 负责：
  - 输入转发
  - 动画播放
  - HUD 更新
  - 结算展示

#### T6. 建立标准局内事件流

建议统一信号输出：
- `swap_started`
- `swap_reverted`
- `matches_found`
- `tiles_removed`
- `tiles_filled`
- `turn_resolved`

目的：
- 降低 UI 对内部实现细节的依赖
- 为后续特殊元素和教程联动留钩子

#### T7. 为特殊元素预留规则接口

本阶段不要求完整做完炸弹和彩虹花，但要预留以下能力：
- 匹配结果可扩展
- tile 不再只表示“基础花朵类型”
- 支持后续加入 tile 属性或特殊行为

### 6.3 交付物

- 收敛后的 `Board` 核心流程
- 精简后的 `GameController` / `SimpleGameController`
- 一版可扩展的局内事件流

### 6.4 验收标准

- 不再存在多套局内规则流程
- 关卡 1、10、20 的元素池与配置一致
- 一次交换后的结果只由单一路径结算
- UI 不直接改写棋盘核心状态

### 6.5 风险

- 改动面较大，若无基础测试，容易引入局内回归 bug

## 七、Phase 3：MVP 闭环期

### 7.1 阶段目标

跑通最小可行闭环：

```text
过关奖励 -> 花园种植 -> 成长/收获 -> 回流局内
```

### 7.2 主要任务

#### T8. 统一花园数据结构

问题：
- `SaveManager` 默认结构与 `GardenUI` 实际使用字段不一致

整改动作：
- 统一 `garden` 数据模型
- 明确 `slots`、`inventory`、`decorations` 的职责
- 增加默认存档结构版本兼容

建议模型：

```text
garden:
  slots: []
  inventory: []
  decorations: []
```

#### T9. 实现最小种植流程

目标：
- 从关卡奖励获得“花种”或“花苗”
- 在花园中种入空槽位

最小实现即可：
- 不做复杂背包系统
- 不做拖拽
- 先做简化的点击种植

#### T10. 实现成长与收获逻辑

目标：
- 依据 `planted_at` 和当前时间计算成长进度
- 成长完成后可收获
- 收获产出资源

建议：
- 先做离线时间结算
- 不做复杂定时器驱动

#### T11. 建立资源回流

目标：
- 花园产出能用于局内

建议第一版回流方式二选一：

方案 A：
- 花园产出 `stars`
- `stars` 可用于失败后继续或购买提示

方案 B：
- 花园产出 `boost`
- `boost` 可换取开局加步数或局内道具

建议优先 A，复杂度更低。

#### T12. 实现“休息时刻”最小版本

目标：
- 将设计文案变成系统机制

建议最小版本：
- 失败后显示“休息时刻”
- 保留少量阶段进度奖励
- 可消耗 `stars` 或广告占位继续

### 7.3 交付物

- 统一的花园数据模型
- 可种植、可成长、可收获的基础花园
- 一版局外资源回流逻辑
- 一版“休息时刻”最小机制

### 7.4 验收标准

- 玩家完成关卡后能拿到可用于花园的奖励
- 花园中至少存在“种植 -> 成长 -> 收获”闭环
- 收获资源能影响下一局
- 失败后不只是弹窗，而是存在真实恢复/补偿规则

### 7.5 风险

- 若回流资源没有实际用途，闭环仍然是伪闭环
- 若数值设计缺失，可能导致花园价值过低或过强

## 八、Phase 4：稳定性补强期

### 8.1 阶段目标

将整改后的核心路径纳入测试和基本质量控制，避免下一轮迭代回退。

### 8.2 主要任务

#### T13. 扩展自动化测试覆盖

优先补以下测试：
- 关卡推进测试
- 当前关卡重开测试
- 棋盘初始化读取元素池测试
- 补牌后无非法状态测试
- 花园存档结构测试
- 花园成长与收获测试

#### T14. 增加关键流程回归检查清单

建议形成固定回归项：
- 进入游戏
- 开始关卡
- 完成一次有效交换
- 成功通关
- 失败结算
- 进入花园
- 种植
- 收获
- 重启后存档恢复

#### T15. 清理过时文档和虚假完成项

需要同步修正的文档包括：
- `README.md`
- `DEVELOPMENT_PLAN.md`
- `TEST_DOCUMENTATION.md`

目的：
- 避免文档宣称已完成而代码实际未完成
- 保证团队后续协作基于真实状态

### 8.3 交付物

- 更新后的测试用例
- 基础回归清单
- 同步后的项目文档

### 8.4 验收标准

- 关键主流程具备自动化测试或明确回归脚本
- 文档描述与代码状态一致
- 新增改动能通过最低限度回归验证

## 十三、最终结论

本轮技术整改的本质不是“修几个 bug”，而是：

> **把当前“三消原型 + 系统骨架”的工程，收敛为一个可持续迭代的 MVP 基础版本。**

若整改顺利完成，项目将获得三项核心收益：

1. 局内规则清晰，后续扩展成本下降
2. 局外成长闭环成立，产品形态更接近真实目标
3. 测试与文档同步，团队协作成本下降

因此，建议项目后续开发顺序严格遵循：

```text
先结构收敛 -> 再主循环闭合 -> 再内容扩展 -> 最后商业化深化
```
