# 星光花园 - 迭代 A 目标对齐与验证清单

## 文档目标

本文件用于把 [STATUS_AND_ITERATION_PLAN.md](./STATUS_AND_ITERATION_PLAN.md) 中的“迭代 A：闭合最小主循环”转换为可验证、可评估、可持续迭代的交付清单。

使用原则：

- 不以排期驱动，而以产品目标一致性驱动
- 每项功能都必须回答“服务哪个产品目标”
- 每项交付都必须具备“可验证标准”
- 每轮完成后都必须能被评估，而不是只看代码是否写完

---

## 1. 迭代 A 目标

本轮只做一件事：

> 把“消除 -> 奖励 -> 花园成长 -> 合成 -> 局内反哺”做成真正可感知的主循环。

本轮不做：

- 好友/排行榜
- 剧情章节
- 花园装饰大系统
- 微信分享裂变
- 复杂商业化接入

当前实现状态：

- `P0-1` 已完成
- `P0-2` 已完成
- `P0-3` 已完成
- `P0-4` 已完成最小版
- `P0-5` 已完成最小版
- `P1-1` 已在当前代码能力下满足基础要求

---

## 2. 产品目标对齐

### 2.1 玩家视角目标

玩家在这一版中应能明确感知：

1. 每打一局都能带回花园资源。
2. 花园不是摆设，而是能成长和合成。
3. 合成后的结果会让下一局更轻松。
4. 即使失败，也不会完全白打。

### 2.2 产品验收目标

- 首日用户在 3 局内理解完整主循环。
- 花园与关卡之间存在至少 2 条明确资源往返关系。
- 玩家失败后仍能保留部分成长收益。
- 合成是可见、可用、可期待的，而不是隐藏数据逻辑。

## 4. 本轮要补齐的系统

### P0-1 统一关卡奖励结算

状态：已完成

目标：

- 结束关卡时统一发放奖励，而不是散落在控制器逻辑中。

产品目标对应：

- 让玩家确认“每局都能带回资源”
- 让奖励成为主循环的稳定入口

策划要求：

- 胜利结算至少展示：
  - 星级
  - 分数
  - 本局获得花种
  - 本局获得星光
- 失败结算至少展示：
  - 本局进度
  - 安慰奖励
  - 是否继续挑战

程序任务：

- 增加统一的 Battle Reward / Settlement 数据结构
- 将过关奖励、失败保底、续关消耗统一收口到一个结算模块
- 让 `PopupManager` 只负责展示，不负责业务结算

测试点：

- 胜利后奖励只发放一次
- 失败后保底奖励正确到账
- 重开关卡不会重复领取上一局奖励

可评估结果：

- 玩家在结算页能直接回答“这一局我拿到了什么”
- 奖励发放逻辑不依赖具体 UI 弹窗实现

---

### P0-2 花种掉落与资源表

状态：已完成

目标：

- 不同关卡应产出不同花种和资源，建立“为了某个目标再打一局”的动机。

产品目标对应：

- 建立目标感
- 建立关卡差异感

策划要求：

- 20 关拆成至少 3 个掉落阶段：
  - 1-5 关：基础 3 色花种
  - 6-12 关：增加第 4-5 种花种
  - 13-20 关：开放更稀有花种或更高掉落量
- 每关至少定义：
  - 主掉落花种
  - 星光基础奖励
  - 首通额外奖励

程序任务：

- 在关卡配置中增加奖励字段
- 补充读取与发放逻辑
- 奖励信息接入胜利弹窗/结算页

测试点：

- 关卡配置未填奖励时有默认值
- 奖励能正确写入库存与玩家数据
- 首通奖励不会重复发放

可评估结果：

- 玩家能区分“这关值得打什么”
- 不同区间关卡在奖励上有明确差异

---

### P0-3 花园合成系统最小版

状态：已完成

目标：

- 把“收集 -> 种植 -> 收获”升级为“收集 -> 种植 -> 收获 -> 合成 -> 再投入”。

产品目标对应：

- 建立局外成长追求
- 让花园从展示层变成玩法层

最小规则：

- 两个同类型同等级花种/花朵，可合成一个高一级花种
- 本轮只做 3 级：
  - Lv.1 花种
  - Lv.2 花苗
  - Lv.3 星光花
- Lv.3 收获收益明显高于 Lv.1

策划要求：

- 合成需要明确反馈：
  - 合成按钮
  - 消耗预览
  - 结果预览
  - 成功反馈
- 合成失败不做概率设计，本轮只做确定性合成

程序任务：

- 扩展 `garden.inventory` 数据结构，支持等级管理
- 在 `GardenUI` 增加合成入口
- 增加合成校验、扣除、产出、提示

测试点：

- 数量不足时不可合成
- 合成后旧物品正确扣减
- 合成后新等级物品正确入库

可评估结果：

- 玩家会主动尝试合成而不是只收获
- 高等级花的收益足以驱动下一轮行为

---

### P0-4 星光反哺局内

状态：已完成最小版

目标：

- 星光不只用于续关，至少提供第二个明确消费场景。

产品目标对应：

- 建立局外资源价值
- 建立花园成长对局内的明确反哺

建议本轮只做两种用途：

- 用途 A：失败后继续挑战 +5 步
- 用途 B：开局购买一次轻道具

当前已实现：

- 开局 +3 步（星光祝福）

后续可选扩展：

- 开局刷新一个提示机会

策划要求：

- 星光消耗要低门槛，让玩家愿意首次尝试
- 不做复杂商店，先放在开局面板或关卡内快捷按钮

程序任务：

- 增加星光消费接口
- 在开局前增加轻量准备 UI
- 道具效果接入 `LevelSystem`

测试点：

- 星光不足时禁止购买
- 消耗成功后本局立即生效
- 退出重开不重复继承临时效果

可评估结果：

- 玩家能说出星光至少两个用途
- 局外资源的积累会影响局内策略选择

---

### P0-5 “休息时刻”规则化

状态：已完成最小版

目标：

- 把失败治愈感从文案升级为系统规则。

产品目标对应：

- 降低失败挫败
- 强化“没有失败，只有休息时刻”的品牌表达

当前已实现规则：

- 失败时按本局完成度发放保底奖励
- 保底奖励至少包含：
  - 少量星光
- 连续失败 2 次后，额外发放鼓励星光与 1 个基础花种

策划要求：

- 奖励规模不能高于正常通关
- 但要足以让玩家感知“没有白玩”

程序任务：

- 记录本局完成度
- 增加失败保底奖励结算
- 增加连续失败计数与重置逻辑

测试点：

- 通关不会触发失败保底
- 连续失败计数在通关后重置
- 免费鼓励奖励不会无限触发

可评估结果：

- 玩家失败后仍愿意继续下一局
- 失败反馈被感知为安慰，而不是二次打击

### P1-1 关卡配置真正驱动棋盘

状态：基础能力已满足

目标：

- 让关卡差异来自配置，而不是只有步数和目标变化。

产品目标对应：

- 提升关卡内容表达力
- 为后续特殊元素与主题关卡预留扩展能力

本轮要求：

- `available_types` 对棋盘初始化和补牌全量生效
- 预留特殊元素概率字段，但本轮不强上完整炸弹/彩虹玩法

程序任务：

- 检查 `Board.gd` 的初始化与补牌流程是否完全读取关卡配置
- 为后续特殊元素生成预留统一入口

测试点：

- 指定 3 种元素时，整局只出现这 3 种
- 补牌阶段不会生成未配置元素

可评估结果：

- 关卡配置真正成为玩法驱动源
- 后续新增规则不需要重写棋盘核心结构

## 5. 交付判断原则

以下情况不算完成：

- 代码已写，但玩家无法感知功能价值
- 界面已做，但资源流没有闭合
- 逻辑已通，但缺少自动化验证
- 单点功能可用，但无法映射到整体产品目标

以下情况才算完成：

- 有明确的目标映射
- 有可重复验证的验收标准
- 有玩家可感知的结果
- 有后续可评估的数据或观察口径

## 6. 数据设计建议

### 5.1 关卡奖励字段

建议在关卡配置中新增：

```json
{
  "rewards": {
    "seed_type": 1,
    "seed_count": 1,
    "stars": 20,
    "first_clear_bonus": {
      "stars": 30,
      "seed_count": 1
    }
  }
}
```

### 5.2 失败保底字段

建议在结算模块中统一计算：

```json
{
  "progress_ratio": 0.6,
  "rest_rewards": {
    "stars": 6,
    "seed_type": 1,
    "seed_count": 0
  }
}
```

### 5.3 合成规则表

建议独立配置：

```json
{
  "synthesis_rules": [
    { "from_level": 1, "to_level": 2, "cost_count": 2 },
    { "from_level": 2, "to_level": 3, "cost_count": 2 }
  ]
}
```

## 7. UI 需求补充

### 6.1 结算页

- 胜利与失败都应改为“结果页”思路
- 至少显示资源变化前后对比
- 明确告诉玩家资源去了哪里

### 6.2 花园页

- 背包区要能区分等级
- 增加“合成”入口
- 合成完成后有明确视觉反馈

### 6.3 开局准备页

- 进入关卡前给一个极轻量准备步骤
- 只提供 1 个可购买辅助项
- 避免做成复杂商店页

## 8. 程序拆分建议

### 模块建议

- `SettlementService`：统一局内结算与奖励发放
- `RewardConfig` / 关卡奖励字段：负责奖励来源
- `GardenSynthesisService`：负责合成校验和执行
- `EconomyService`：统一星光增减和消耗日志

### 现有代码优先调整点

- 收口 `SimpleGameController` 中的奖励发放逻辑
- 避免 `PopupManager` 直接承担业务逻辑
- 让失败继续、失败保底、胜利奖励都走统一结算流程

## 9. 测试清单

### 自动化测试建议新增

- 胜利结算奖励测试
- 失败保底奖励测试
- 首通奖励唯一性测试
- 合成成功/失败测试
- 星光消费测试
- 开局道具生效与重置测试
- 配置驱动补牌测试
- 连续失败缓冲触发测试

### 手动体验验收

- 新玩家首轮进入后，能否在 3 局内理解主循环
- 花园操作是否足够直观
- 合成是否比单纯种植更有吸引力
- 失败时是否真的感受到“被安慰”，而不是“换皮失败”

### 评估问题

每次完成迭代 A 子项后，至少回答以下问题：

1. 这项功能服务了哪个产品目标？
2. 玩家能否在 1 次体验内感知它的价值？
3. 它有没有形成新的资源流或行为驱动？
4. 如果移除它，主循环是否会明显变弱？

## 10. 整体验证矩阵

| 验证维度 | 问题 | 通过标准 |
|------|------|------|
| 目标一致性 | 该功能是否直接服务核心循环闭合？ | 能明确映射到奖励、成长、合成、反哺之一 |
| 用户感知 | 玩家是否能看见并理解变化？ | 1-3 局内可感知 |
| 资源闭环 | 新资源是否有来源、用途、反馈？ | 三者完整存在 |
| 可测试性 | 是否能写成自动化测试或稳定手测步骤？ | 可以 |
| 可评估性 | 完成后是否能判断值不值得保留？ | 可以通过体验或数据口径判断 |

## 11. 本轮完成定义

满足以下条件，可认为“迭代 A 完成”：

1. 玩家每局都能带回稳定奖励。
2. 花园支持种植、收获、合成三段式成长。
3. 星光具备至少 2 个明确消费场景。
4. 失败后有规则化保底奖励。
5. 玩家能理解“为什么继续打一局”。

当前判断：

- 上述 5 条已基本满足
- 因此迭代 A 主循环骨架已达成
- 后续建议转入体验优化与内容层补强，而不是继续扩写主循环结构
